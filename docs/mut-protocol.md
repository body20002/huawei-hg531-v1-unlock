# Huawei MUT protocol — byte‑by‑byte

Reverse‑engineered from Huawei's `HuaweiMUT.exe` / `MUT_eng.exe` and cross‑checked against
the community Python re‑implementation
([Rezurmas/huawei-mut-unbrick-tool](https://github.com/Rezurmas/huawei-mut-unbrick-tool)).
This is what `tools/mut_flash.py` implements.

## 1. Network layer

| Param | Value | Notes |
|---|---|---|
| Protocol | UDP | no TCP/HTTP/TFTP fallback |
| Destination | `224.0.0.119` | multicast |
| Port | `13456` | both **destination and source** bind |
| Multicast TTL | `0` in the original | local segment only; we used `4` to dodge picky switches |
| `IP_MULTICAST_LOOP` | `1` | |
| `IP_ADD_MEMBERSHIP` | `224.0.0.119` on the chosen NIC | |
| `SO_BROADCAST` | `1` | we also send to `255.255.255.255` as a snooping fallback |

> Any **IGMP‑snooping** switch between the sender and the router will swallow the multicast.
> Disable snooping, or use the broadcast fallback.

## 2. Packet structure — 1086 bytes

```
offset  len  field
0       4    control_word      (LE uint32)
4       4    chunk_counter     (LE uint32, sequence)
8       4    chunk_crc32       (LE uint32)  CRC32 of the 1024‑byte chunk (zero‑padded)
12      4    total_file_size   (LE uint32)
16      4    firmware_crc32    (LE uint32)  CRC32 of the whole image
20      20   PACKAGE_ID        (ASCII, NUL‑padded)
40      2    unknown_word      (usually 0)
42      20   PRODUCT_ID        (ASCII, NUL‑padded)
62      1024 chunk_data        (firmware chunk, zero‑padded if short)
```

## 3. control_word

```
control_word = (opcode << 29) | 0x00000400
```

| opcode | meaning | control_word |
|---|---|---|
| 1 | DATA (full 1024‑byte chunk) | `0x20000400` |
| 2 | LAST (final chunk, zero‑padded) | `0x40000400` |
| 4 | INIT (partition table) | `0x80000400` |

## 4. INIT payload (opcode 4)

Sent first; carries the **partition table**, 32 bytes per partition:

```c
struct entry {          // 32 bytes
  char     name[20];    // ASCII, NUL‑padded  ("CFE", "kernelfs", ...)
  uint32_t start;       // LE
  uint32_t end;         // LE
  uint8_t  flag;        // 2 = cover, 1 = uncover
  uint8_t  pad[3];
};
```

For the HG531 V1 the `.ini` gives:

```
PARTITIONS=CFE,0x00000000-0x0000FFFF,uncover|kernelfs,0x00010000-0x003FFFFF,cover
```

`uncover` for `CFE` ⇒ the bootloader may not be overwritten ⇒ the image is flashed only
to `kernelfs` (`0x10000`–`0x3FFFFF`), preserving the bootloader.

## 5. DATA / LAST (opcodes 1 / 2)

* DATA: `chunk_data` = 1024 bytes copied from `offset = seq * 1024`.
* LAST: final (short) chunk, zero‑padded to 1024; `chunk_crc32` is computed over the
  **padded** chunk.

## 6. PACKAGE_ID / PRODUCT_ID

ASCII, NUL‑padded to 20 bytes. For the HG531 V1: `fnt-HGW` / `fnt-HGW`
(taken from the firmware `.ini`). Other Huawei models differ (`mbb-CPE`, etc.) — always
take them from the matching `.ini`.

## 7. INI file

```ini
# autogenerated by tools
IMAGE_NAME=HG531V1V100R001C105B011_multicast_packet.bin
IMAGE_SIZE=3628242
PACKAGE_ID=fnt-HGW
PRODUCT_ID=fnt-HGW
FIRMWARE_VERSION=0
PCB_VERSION=0
FIRMWARE_CRC_SUM=4163246564
PARTITIONS=CFE,0x00000000-0x0000FFFF,uncover|kernelfs,0x00010000-0x003FFFFF,cover
INI_CRC_SUM=2459307776
```

`FIRMWARE_CRC_SUM` = `zlib.crc32(image)`.
`INI_CRC_SUM` = `zlib.crc32(all_bytes_before_the_INI_CRC_SUM_value)`.

## 8. Send loop

```
repeat:
    send INIT (partition table)
    for each 1024‑byte chunk:
        send DATA   (or LAST for the final, padded chunk)
    (short pause)
```

The original tool defaults to a single pass but keeps sending while "updating"; we loop
continuously and power‑cycle the router so its bootloader catches a clean pass.

## 9. What the router does

1. Listen on UDP 13456 + join `224.0.0.119` during the boot window.
2. INIT → load partition table. DATA/LAST → buffer `RAM[seq*1024]`.
3. After LAST → verify `firmware_crc32`.
4. OK → (optionally verify signature on some models) → write the flash per the partition
   table → reboot. **All checks pass ⇒ it boots the new image.**
